Acceptance check: either wire them as real internal PDF links (verify with a PDF link-extraction check, not just visual inspection) with link text that stands alone ("Voir priorité 1 : lenteur d'affichage", not bare "Voir"), or replace with plain text ("priorité 1") if internal linking isn't in scope this session.

Acceptance check: run `pdftotext` (or equivalent extraction) on the regenerated PDF and confirm no uppercase label extracts with internal spaces inside words. Separately, test with a screen reader (NVDA or VoiceOver) that these labels are announced as whole words.

**7. `[NEW]` Parentheses and some punctuation are dropped from the extracted text layer in several places**, even where surrounding text extracts fine: `DGCCRFLoi n° 2023-171` (missing close-paren before "Loi"), `Critère 1.3.1 Information et relations)` (missing open-paren), `Lighthouse), à titre illustratif` context (open-paren missing upstream), `(Phocuswright, The AI Surge, 2026 .` (missing close-paren). ## P1. Claims that don't survive a technical read

**8. `[REGRESSION]` A heuristic signal is presented as a WCAG criterion failure, at a much larger scale than before.** Page 8 ("Critères WCAG 2.2 niveau AA en échec") lists "1.1.1 Contenu non textuel, 19 constats, 157 occurrences, 20 pages" as a criterion in échec. Page 13 reveals the rule generating those 19 constats is `alt-text-quality-heuristic`. Page 12 (methodology) correctly describes it as "un signal heuristique sur la qualité des textes alternatifs", not a conformance failure. So the conformance table asserts a hard criterion failure using data the methodology page itself says is heuristic, and that single heuristic supplies 157 of 176 total accessibility occurrences (89 percent) and 19 of 22 accessibility findings.

This is exactly the class of problem `docs/milestone-8-scope-addendum.md` section 1.4 anticipated and tried to prevent: "The report methodology section should state plainly that alt text below what this heuristic catches may still benefit from a manual review, rather than implying full coverage." The methodology page does state that. The conformance table does not respect it: it folds the heuristic into the same table as genuine axe-core criterion failures with no visual or structural distinction.

Fix, not a copy tweak: the WCAG conformance table (section 07) must only include criteria where every contributing rule is a genuine deterministic conformance check (axe-core rule mapped to a WCAG success criterion), never a heuristic. `alt-text-quality-heuristic` findings move to their own clearly labeled block, e.g. "Signaux à vérifier" or "Alertes de qualité (non-conformité non confirmée)", with copy stating explicitly that these are heuristic flags, not confirmed criterion failures. Once separated, criterion 1.1.1 either drops out of the conformance table entirely for this site or is recomputed from only the non-heuristic contributing rules, whichever is accurate.
Acceptance check: no row in the WCAG conformance table (section 07) can be sourced, even partially, from a rule tagged as heuristic in `core`. Add a test asserting this at the data layer, not just eyeballing the output. Regenerate and confirm the criterion count on page 5 and the criterion table on page 8 both drop the heuristic-only criterion (should read 2 criteria in échec on 9 pages, not 3 on 20, if 1.1.1's only contributing findings are the heuristic ones).

**9. `[NEW]` Severity language contradicts itself between the performance table and the priorities/appendix sections.** Page 10 (Mesures de performance) grades TBT 560 ms as "à améliorer" and Speed Index 4,4 s as "à améliorer" using its own three-tier scale (bon / à améliorer / insuffisant). Pages 6 and 13 to 14 label the underlying findings for those same metrics `Critique`, the highest severity tier in the whole report. The glossary (page 16) defines Critique as "bloque une tâche essentielle pour une partie des utilisateurs". A 560 ms blocking time does not block an essential task by that definition.
This is a structural problem: performance metrics are being run through two different severity systems (Lighthouse's own bon/à améliorer/insuffisant scale, and the report's four-tier critique/sérieux/modéré/mineur scale) with no reconciliation, and they disagree.
Fix options to weigh (flag for Jules, don't just pick silently): either (a) stop labeling perf metric findings with the same four-tier severity vocabulary used for accessibility conformance, since they're answering a different question, or (b) recalibrate the mapping from Lighthouse thresholds to the four-tier scale so "à améliorer" cannot map to "Critique". Recommend (b), since (a) is a bigger scope change.
Acceptance check: for every performance finding, the severity label shown in the priorities/appendix sections must be consistent with the bon/à améliorer/insuffisant status shown in the performance table, under whatever single mapping is chosen. Add a test enumerating the Lighthouse threshold-to-severity mapping and asserting no metric currently graded "à améliorer" or better can produce a "Critique" finding.

**10. `[NEW]` "20/20 pages avec au moins un constat critique" is manufactured entirely by the perf-severity miscalibration in item 9.** The four perf-critical rules (f002 TBT, f003 FCP, f004 LCP, f006 Speed Index) hit all 20 pages by construction, since they're page-level Lighthouse metrics, not content-dependent findings. **11. `[NEW]` Page 10 undercuts its own numbers: "Valeurs médianes agrégées sur les 20 pages (Lighthouse), à titre illustratif."** "À titre illustratif" (illustrative only) tells a technical reader they can disregard the table. Acceptance check: replace "à titre illustratif" with a caveat that names the actual limitation (e.g. "Simulation mobile avec limitation réseau, passage unique, données de laboratoire et non de terrain"), or remove the caveat if the methodology section (page 12) already covers it adequately and cross-reference it instead of duplicating a vaguer version.
